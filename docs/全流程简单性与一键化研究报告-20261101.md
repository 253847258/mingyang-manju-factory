# 全流程简单性与一键化研究报告

- 日期：2026-11-01
- 方法：10 条逻辑审查线 + 4 个只读子审查线程 + 主线程全量回归/Playwright 实测
- 结论口径：可运行 ≠ 可一键；技术链路通 ≠ 企业级生产闭环

---

## 一、总判断

### 当前是否真正“一键完成全部模块任务”？

**不是。**

现有制片 Agent 最准确的运行方式是：

```text
点 1 次开始
→ 自动跑 5 个免费阶段：需求解析 → 建演员 → 小说与大纲 → 剧本与分镜 → 画布铺开
→ 到关键帧付费闸门停下
→ 人工批准 + 输入确认码
→ 人工再点继续
→ 到视频付费闸门再批准 + 确认码
→ 人工再点继续
→ 成片 → QC → 交付
```

即：

**1 次开始 + 2 次付费批准 + 2 次确认码 + 多次继续执行。**

它能一键跑“技术流水线”，但还不能一键完成“受控、可审计、可交付”的生产闭环。

### 总体自动化判断

| 范围 | 当前判断 |
|---|---|
| 离线功能验收 | 已达到可重复验收 |
| 单模块主要功能 | 多数已落地 |
| 模块间自动串联 | 部分完成，存在旁路和重复数据源 |
| 一键完整生产 | 未完成 |
| 企业级无人值守 | 未完成 |
| 内容语义自动理解 | 结构化字段有基础，剧情/状态连续性不足 |

## 二、10 线程审查总表

| 线程 | 模块 | 输入 → 输出 | 自动化程度 | 能否一键完成模块全部任务 |
|---|---|---|---|---|
| 1 | 引擎与基础设施 | 配置/任务 → 服务、桥接、队列 | 高 | 基础设施可一键启动，但真实账号能力受限 |
| 2 | 演员矩阵 | 演员设定/参考图 → 演员卡、图片、画布节点 | 中 | 否，需人工设计、选图、选角 |
| 3 | 小说工坊 | 参数/角色 → 章纲、内容卡、资产计划、正文 | 中 | 否，四步分开触发，正文逐章 |
| 4 | 剧本工厂 | 小说/角色 → 分集、剧本、分镜 | 中 | 否，缺全部剧本+分镜+送审一键链 |
| 5 | 分镜提示词 | 分镜 → 正负提示词、角色/地点引用 | 中高 | 能批量生成，不能自动判断叙事意图是否准确 |
| 6 | 制作台 | 分镜/关键帧 → 视频 → 整集成片 | 技术高、生产低 | 技术流水线可一键，治理闭环不可一键 |
| 7 | 后期精修 | 镜头/成片 → 时间线、版本、审片、工程包 | 高 | 单模块内可一键渲染，前后模块未自动跳转 |
| 8 | QC/交付/Publish | 成片/字幕/资产 → QC、ZIP、出海物料 | 中高 | 可自动生成，但不强制 QC/审片/锁版 |
| 9 | 制片 Agent/闸门 | 一句话需求 → 十阶段生产 | 中 | 免费阶段自动，付费阶段多次人工 |
| 10 | 数据治理 | 资产/血缘/成本/订单/checkpoint | 基础具备、接入弱 | 不能一键闭环 |

## 三、每个模块的内容衔接与自动理解

### 线程 1：引擎与基础设施

**已自动**

- `start.sh` 统一拉起主服务、出图桥、视频桥。
- 健康检查、队列、任务恢复、错误中文提示已具备。
- 本地环境文件可承载密钥，`check:secrets` 通过。

**缺口**

- 火山真实模型仍受 Safe Experience Mode 限制。
- 真实模型/余额/发布账号仍依赖外部授权。
- 服务一致性依赖单实例守卫，不是多机集群。

---

### 线程 2：演员矩阵

**输入**

- 姓名、性别、年龄、角色类型、画风、外貌、服装、人设、提示词、参考图、画布位置。

**输出**

- 演员表、定妆图、主图/参考图、画布人物/场景/物品节点、关系连线。
- `actor_ids` 可写入小说选角。

**自动衔接**

- 演员加入小说后，小说能自动读取演员结构化资料。
- 内容卡和资产计划能复用演员 ID。

**不能一键的原因**

- 没有“建演员 → 生成定妆 → 选主图 → 建参考图 → 放入画布 → 加入小说”的总任务。
- 角色设计、主参考图、画风批准仍需人工。
- 章纲出现新角色不会自动建演员卡。
- 角色匹配只认精确 ID 或同名，别名/称谓/同名异人不可靠。

---

### 线程 3：小说工坊

**输入**

- 小说参数、演员/自定义角色、故事框架、参考范本、章纲范围、内容卡、资产提示词、画布、正文要求。

**输出**

- 章纲版本、章节内容卡、章级资产计划、画布节点/连线、正文、正文历史、操作记录。

**已自动理解**

- 章纲有章首、章末、承接、钩子和事件。
- 内容卡有目标、冲突、转折、结果和 3–8 个情节 beat。
- 资产计划自动按章节建立人物/环境/物品映射。
- 续写提示词会带本章内容卡、资产、前三章正文结尾和已有正文。

**断点**

1. 四步是四个独立任务，没有“一次提交跑完四步”。
2. 正文只有逐章续写/重写，没有“从断点继续全书”。
3. 剧情连续性不硬拦，可直接写第 50 章。
4. 重写整章走旧写作链路，不读取四步内容卡，和续写上下文不一致。
5. AI 内容卡失败后模板降级仍算完成，没有质量确认门。
6. 四步资产计划没有写入正式 `assets`、快照、血缘、成本、订单。
7. 参考图仍要人工填写或去演员矩阵生成。

**判断**

小说工坊是“半自动生产线”，不是无人值守一键写作。

---

### 线程 4：剧本工厂

**输入**

- 小说、章节、大纲、形态、时长、集数、画风、演员和可选画布资产。

**输出**

- 分集计划、剧本、场景/Beat、分镜、提示词、审核状态、导出文件。

**已自动**

- 小说 → 分集规划 → 单集剧本 → 分镜是可执行任务链。
- 镜头结构包含景别、机位、运镜、时长、动作、对白、情绪、成本级、角色/地点引用。

**不能一键的原因**

- 缺“全部剧本正文 → 全部分镜 → 全部体检 → 全部送审”的一键链。
- 资产到剧本仍靠人工绑定。
- 正式库 180/180 集仍是 draft。
- 整季流水线存在审核/契约/锚定绕过风险。

---

### 线程 5：分镜提示词与内容理解

**已结构化**

- 角色/地点 ID 进入 `refs`。
- 正负向提示词、景别、机位、运镜、时长、动作、对白、情绪已落库。
- 有提示词清洗和 linter。

**缺口**

- 没有镜头级 `intent / dramatic_beat_id / start_state / end_state`。
- 没有人物关系、道具状态、人物位置、伤势、服装状态账本。
- 提示词质量检查不是硬门禁。
- 正式数据存在重复角色锚点、超长镜头、0 首尾帧使用。

**判断**

下游可以“读懂字段”，但还不能稳定“读懂戏”。

---

### 线程 6：制作台

**输入**

- 剧集、镜头、提示词、角色/地点引用、关键帧、尾帧、视频后端、字幕/音频设置。

**输出**

- 关键帧、视频、整集成片、任务进度、版本和报告。

**已自动**

- 整季流水线可选阶段，一次提交可跑技术链。
- 关键帧 → 视频 → 成片有真实测试覆盖。

**不能生产级一键的原因**

- 真实视频成功数为 0，正式完成视频全部是 placeholder。
- 审核、锚定、契约默认 warn。
- 首尾帧正式使用率 0。
- 付费批准后仍要人工继续。
- 资产快照、血缘、成本、订单没有自动接入。

---

### 线程 7：后期精修

**输入**

- 镜头/成片、四轨时间线、裁剪/转场/字幕/音频参数、版本和审片意见。

**输出**

- 成片 MP4、时间线版本、审片状态、审计、EDL/FCP7/OTIO 工程包。

**优势**

- 单模块自动化较成熟。
- 审片状态机、版本树、乐观锁、审计有效。

**断点**

- 模块 4 成片完成后不会自动创建/打开精修时间线。
- 精修页没有 QC/交付/Publish 一键入口。
- 审片意见没有绑定具体版本。
- 精修保存/重渲染后不会自动退回待审。

---

### 线程 8：QC、交付与 Publish

**已自动**

- QC 覆盖流、编码、分辨率、时长、黑帧、静音、响度、缺镜、字幕 CPS、跨镜一致性。
- 交付包含成片、字幕、分镜、素材、报告、QC、EDL/FCP7/OTIO、多平台版本。
- Publish 能生成多语言字幕、封面和发布元数据。

**硬缺口**

- QC error 仍可交付。
- 未审片或未锁定版本仍可交付。
- 占位素材、失败镜头不是硬阻断。
- Studio 的 deliver/publish 依赖 finish，不依赖 QC。
- 交付按最新成片取文件，可能拿到不是审片通过的那一版。
- 精修字幕轨和交付 SRT 可能不是同一份。
- Publish 只是物料生成，不是真正平台发布。

---

### 线程 9：制片 Agent、一键编排与闸门

**自动范围**

`brief → cast → novel → script → canvas`

**人工门**

`keyframe`、`video` 两次付费批准与确认码。

**严重问题**

- `/api/canvas/run`、`/api/canvas/run-node` 仍可直接执行画布，构成绕过审批的旁路。
- 审核闸门只保护 `/api/render/*`，不保护 `/api/studio/*` 和画布执行链。
- 镜头契约和锚定默认 warn。
- `force:true` 可绕过，审计失败被吞掉。
- Studio 交付不要求审片/锁版/QC。

**判断**

现在有“编排器”，但还没有“唯一执行门面 + 统一门禁内核”。

---

### 线程 10：数据治理与内容事实层

**已有基础**

- 资产实体/版本/快照/血缘/成本/订单/checkpoint 表与 API。
- `job_steps` 可记录章纲批次和内容卡步骤。

**当前真实库**

- 资产 123 条。
- `project_id` 为空 123/123。
- 资产快照 0。
- 生成血缘 0。
- 成本台账 0。
- 生产订单 0。
- checkpoint 只接入小说章纲/内容卡，未覆盖全部媒体节点。

**主要问题**

- 三套资产表示并存：
  1. `actors` + 画布节点；
  2. 小说 pipeline JSON 资产计划；
  3. 正式 `assets/asset_versions`。
- 没有统一 Run Manifest。
- 没有统一 Schema 版本。
- 订单、成本、血缘大多靠人工 API 写。
- 重启后任务主要是标失败，不是自动重新挂载。

## 六、P0 改进清单

### 1. 统一执行门面

所有付费生成只允许经过一个 Runner：

```text
Studio / 画布 / 批处理 / Agent
        ↓
唯一 ExecuteGate
        ↓
剧本审核 / 镜头契约 / 锚定 / 资产快照 / 预算 / 人工确认
        ↓
模型调用
```

必须关闭或封装：

- `/api/canvas/run`
- `/api/canvas/run-node`

---

### 2. 批准后自动续跑

人工只批准，不再人工反复点“继续”：

```text
批准关键帧 → 自动执行 → 自动进入视频待批准
批准视频 → 自动执行 → 自动成片 → 自动 QC → 自动准备交付
```

---

### 3. 资产快照成为开拍硬条件

每次付费生成必须带：

- `asset_snapshot_id`
- `script_version`
- `shot_id`
- `prompt_hash`
- `cost_reservation_id`

没有资产快照，不允许关键帧/视频。

---

### 4. 交付硬门禁

交付必须同时满足：

- 指定 `timeline_id/version_no`
- 审片为 `approved` 或 `locked`
- 无 open blocker/major
- QC 不是 error
- 无 placeholder/失败镜头
- 资产快照和血缘完整
- 终版文件 hash 写入 manifest

---

### 5. 统一故事事实层

新增一个 Story Bible：

- 人物关系
- 人物状态
- 地点状态
- 道具状态
- 服装/伤势/位置
- 章节事实
- 镜头意图
- 起始状态/结束状态

下游模块只读取这个事实层，不再各自猜 JSON。

---

### 6. 所有生成自动回写治理数据

生成完成自动写：

- `asset_lineage`
- `cost_ledger`
- `production_orders`
- `job_steps`
- episode/shot 的当前产出

不靠人工另点接口。

## 八、Playwright UI 测试结果

### 已通过

- `ui-smoke.py`：30 通过 / 0 失败
- `ui-scale.py`：21 通过 / 0 失败

  - 200 章小说首屏 0.9s

  - 200 镜制作台首屏 2.0s

### 未通过

运行到小说工坊后中断，失败集中在：

- 测试仍按旧版小说 UI 查找“载入演员表”；
- 新四步生产线默认页没有旧参数页的控件；

- 已通过大量演员画布操作，但整份套件未完成。

#### `canvas-audit.py`

已跑出多项真实/夹具问题后中断：

- 空白抽屉仍拦截小地图点击；
- 小地图第一击未改变视口；
- LOD 全档下图片未开始解码；
- 框选多选未生效，导致对齐工具条不可用；
- 之后对齐按钮不可见，审计中断。

这些问题至少说明画布 UI 的 Playwright 可交互性仍未收口，不能只看 Node 单测。

## 九、最终结论

### 做得好的地方

- 单模块能力丰富，技术链能跑。
- 全仓 Node 回归 57/57、3357 断言通过。
- 离线跨模块 E2E 已能跑通审核、快照、尾帧、成片、审片、订单和成本。
- 制片 Agent、编辑审片状态机、QC、交付包都有真实实现。

### 核心问题

不是“模块不够多”，而是：

1. **执行入口不唯一**：有主链也有旁路。
2. **门禁不统一**：审核、契约、锚定、预算、交付各管一段。
3. **资产事实源不唯一**：三套资产表示并存。
4. **版本不绑定**：审片、QC、交付可能对应不同成片版本。
5. **一键不连续**：批准后还要人工反复继续。
6. **内容理解不够深**：字段能传，剧情状态和因果不能自动守。

### 最优先顺序

```text
先封旁路
→ 再做统一 ExecuteGate
→ 再接资产快照/成本/订单/血缘
→ 再让批准后自动续跑
→ 再加交付硬门禁
→ 最后做一键 UI 和内容理解报告
```

**一句话：当前系统已经“能跑”，但还处在多模块拼装阶段；要先收成一个执行入口、一套门禁、一套内容事实，才谈得上真正的一键全流程。**
