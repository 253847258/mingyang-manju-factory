# 排产与自愈使用手册

> 面向**使用者**的操作手册：怎么建排产、怎么看「到点该不该跑」、怎么理解阶段失败自愈（换了什么后端、影响是什么）、怎么恢复暂停的队列、出问题怎么排查。
>
> 本手册只写**已经落到代码里**的名字：所有函数、字段、判定码都逐字对照过 `src/schedules.js`、`src/self-heal.js`、`src/jobs.js`、`src/guard.js`（核对清单见 §9）。设计契约见 `strategist/reports/T-101-schedules-spec.md`、`T-102-selfheal-spec.md`；契约与实现不一致之处记入 §10。

## 0. 两条必须先懂的规矩

### 0.1 「想跑」和「能跑」是两个开关

| 开关 | 存在哪 | 谁的意志 | 关掉以后 |
|---|---|---|---|
| **本条排产启停** `enabled` | `schedules.enabled`（1/0） | 你（针对这一条排产） | 到点不触发；判定码 `skipped_disabled`，**不写台账行、不动水位线、`skip_count` 不增**（`next_run_at` 原样保留，重新启用时才重算） |
| **整座工厂的闸门** 队列暂停 | `app_config` 的 `jobs:paused` 键 | 人（人工暂停）或系统（预算/额度自动暂停） | 所有排产到点都**不建项目、不入队**，只记一条 `skipped_paused` |

一句话：`enabled=1` 只表示「这条排产想跑」，**能不能真跑由队列闸门说了算**。排产永不自动恢复队列（预算是否已放开只有人知道）。

### 0.2 两条红线不会因为「定时」而消失

1. **付费阶段仍然要人工批准 + 确认码**：排产建出来的任务就是一个普通 `studio` 任务（`type:'studio'`、`limit:1`、标题带 `[排产]` 前缀），跑到付费阶段（`keyframe` / `video`）照样停下等批准。定时只解决「什么时候开始」，不解决「要不要花钱」。
2. **内容审核类错误永不换后端**：自愈对 `moderation` 是硬编码红线（`NO_SWITCH_KINDS`），换后端 = 换一个厂商绕过审核，任何配置都改不了这一条。

## 1. 什么时候该用排产

**适合**

- 「每天早上 9 点按同一个需求排一版」→ `kind:'daily'`
- 「每 30 分钟扫一次，有新素材就出一版」→ `kind:'interval'`
- 「每周一重跑某个**既有的**制片项目的质检/成片」→ `mode:'existing_production'`
- 「本周五 20:00 只跑一次活动片」→ `kind:'once'`
- 「复杂节律（工作日 9 点、整点半小时一次…）」→ `kind:'cron'`（5 段简版）

**不适合**

- 需要人盯着每一步的探索性创作（直接用制作台手工跑更省事）
- 想让机器「自己决定要不要花钱」的付费阶段（红线不允许，见 §0.2）
- 想靠排产把停机期间错过的窗口全部补回来烧一堆钱（默认策略就是**不补**，见 §2.5）

## 2. 怎么建一条排产

### 2.1 当前的三个入口

| 入口 | 怎么用 | 说明 |
|---|---|---|
| **Node API（推荐，当前唯一可直接用的入口）** | `import` 后调 `createSchedule(...)` | 模块在 `src/schedules.js`，纯 ESM、零新依赖 |
| **仓库自带离线自测** | `node tests/test-schedules.js` | 跑在临时库/临时配置上，不动你的 `data/`、不花模型钱，用来确认「本机这套功能是通的」 |
| **HTTP / 界面** | 契约规划中的 `GET/POST/PATCH/DELETE /api/schedules`、`POST /api/schedules/:id/trigger`、`POST /api/schedules/tick` 与制作台的排产面板 | **本仓库当前尚未落地**（没有 `src/routes/schedules.js`，`server.js` 也未注册）。用之前请先实测：`ls src/routes/` 与 `grep -rn "api/schedules" src/ server.js`。落地前请用 Node API 或自己写一小段脚本调用 |

> 换句话说：**排产目前是「库」不是「按钮」**。本手册 §2.2 给的是可直接复制运行的 Node 入口。

### 2.2 最小可跑示例（离线，不花钱）

把下面的内容存成仓库根目录下的 `demo-sched.mjs`，然后 `cd ai-video-factory && node demo-sched.mjs`（放在仓库根目录是因为 `./src/...` 这类相对导入是按**脚本所在目录**解析的；想放别处就把这两处 import 路径换成绝对路径）。
它把 `FACTORY_DB` / `FACTORY_DATA_DIR` / `FACTORY_CONFIG` 全部指到临时目录，并且用 `llm.provider:'mock'` + `placeholder` 后端，**离线、零成本、不动你的数据**。

```js
import fs from 'node:fs'; import os from 'node:os'; import path from 'node:path';
const TMP = fs.mkdtempSync(path.join(os.tmpdir(), 'sched-demo-'));
process.env.FACTORY_DATA_DIR = path.join(TMP, 'data');
process.env.FACTORY_DB = path.join(TMP, 'demo.db');
process.env.FACTORY_CONFIG = path.join(TMP, 'config.json');
fs.mkdirSync(process.env.FACTORY_DATA_DIR, { recursive: true });
fs.writeFileSync(process.env.FACTORY_CONFIG, JSON.stringify({
  llm: { provider: 'mock' }, image: { backend: 'placeholder' },
  video: { backend: 'placeholder' }, tts: { backend: 'placeholder' },
}), 'utf8');

const { migrate } = await import('./src/db.js');       // 换成你的绝对路径亦可
const S = await import('./src/schedules.js');
migrate();                                             // 建基础表（排产表由 ensureSchedulesSchema 自建）

const s = S.createSchedule({
  name: '每天 9 点短剧排产',                    // 必填，≤60 字，且不能与已有排产重名
  kind: 'daily', at_time: '09:00', tz: 'Asia/Shanghai',
  mode: 'new_production',
  target: {
    brief: '拍一部 3 集都市悬疑短剧',
    spec: { episodes: 3, episodeSeconds: 60 },
    offline: true,                              // 演练：离线规则兜底，不连外网
    until: 'canvas',                            // 免费阶段为止（付费阶段仍会停下等批准）
  },
  miss_policy: 'skip', grace_min: 5,
});
console.log(s.id, '|', s.summary);              // 例：S-0001 | 每天 09:00（Asia/Shanghai） · 下次 2025-06-01 09:00
console.log('未来 3 次：', S.nextRuns(s, { count: 3 }));

// 干跑：只看「此刻该不该跑」，不建项目、不入队、不落库
const dry = await S.fireSchedule(s.id, { dryRun: true });
console.log(dry.reasonCode, '|', dry.reason);
```

`createSchedule(input, { by:'human', now:new Date() })` 的要点：

- 返回**建好的排产对象**（已落库），`id` 形如 `S-0001`（`nextId('S','schedule')`）。
- `by` 记进 `created_by`（`human` / `agent` / `system`）。
- `now` 可注入固定时刻（写脚本做演练时很有用；内部只是用来算「下一次」和校验 `once_at` 是否在未来）。
- **算不出未来窗口就不落库半成品**：表达式永远算不出下一次（比如「2 月 30 日」）会直接抛中文错误。
- 校验失败一律抛中文 `Error`（示例见 §8.1）。

### 2.3 六种 `kind`：各自要填什么

`SCHEDULE_KINDS = ['once', 'interval', 'daily', 'weekly', 'monthly', 'cron']`

| kind | 必填字段 | 语义 | 说明 |
|---|---|---|---|
| `once` | `once_at` | 只跑一次 | `once_at` 写 `'YYYY-MM-DD HH:MM'`（按 `tz` 解释），必须**晚于当前时刻**；触发成功后本条自动 `enabled=0`、`next_run_at=NULL`，台账记 `done_once` |
| `interval` | `interval_minutes` | 每 N 分钟 | `1~10080` 的整数；按 `anchor_at` 对齐（默认=创建时刻向下取整到分钟），**重启/抖动都不漂移** |
| `daily` | `at_time` | 每天的 `HH:MM` | `'09:00'` |
| `weekly` | `weekdays` + `at_time` | 每周指定星期 | `weekdays` 写 `'1,3,5'`，`0`=周日 … `6`=周六 |
| `monthly` | `day_of_month` + `at_time` | 每月 N 号 | `1~31`；**该月没有这一天就跳过该月**（不顺延到月末，保持「指定日期」语义） |
| `cron` | `cron` | 5 段简版表达式 | 见 §2.4 |

其他字段：

- `tz`：IANA 时区名（`Asia/Shanghai`、`UTC`、`America/New_York`），默认 `Asia/Shanghai`。非法时区报 `无效时区：Bad/Zone（请用 IANA 名称，如 Asia/Shanghai / UTC）`。
- `mode`：`new_production`（默认，新建制片项目）| `existing_production`（对既有项目重跑，此时 `target.productionId` 必填且必须存在）。
- `target`：JSON 对象，字段与制片入参对齐：
  - `brief`：一句话需求（`new_production` 时 `brief` 与 `spec` 至少给一个）
  - `spec`：制片参数（`episodes` / `episodeSeconds` / `ratio` / `reuseActors`…）
  - `offline`：`true` = 离线规则兜底（演练/自检用，不连外网）
  - `provider`：LLM provider 覆盖（`null` = 用全局配置）
  - `skill`：技能 id
  - `until`：跑到哪个阶段为止（默认 `'all'`；写 `'canvas'` 这类免费阶段就只跑到那里，付费阶段仍会停下等批准）
  - `productionId`：仅 `mode:'existing_production'` 用

> 小坑：`name` 是**唯一**的。同名会抛 `排产名称已重复：xxx（已存在 S-0002，请换一个名字或先改那条排产）`。

### 2.4 `cron` 简版语法（明确边界）

段序：`分 时 日 月 周`；范围：分 `0-59`、时 `0-23`、日 `1-31`、月 `1-12`、周 `0-6`（`0`=周日，**也接受 `7`=周日**，内部归一到 0）。

每个字段支持：`*`、`N`、`A-B`、`A,B,C`、`*/N`、`A-B/N`（列表元素可以是区间或步进）。

**不支持**（会抛中文错误，不静默忽略）：秒级第 6 段、`MON`/`JAN` 名称、`@daily` 之类宏、`L/W/#/?` 扩展。

```text
0 9 * * 1-5      → 工作日 9:00
*/30 * * * *     → 每 30 分钟
0 9 1 * 1        → 每月 1 号「或」每周一 9:00（日与周同时受限时按 OR 语义，与 Vixie cron 一致）
```

报错示例：`cron 表达式非法：'0 9 * * 8'（周字段超出范围 0-6（0=周日；也接受 7=周日）（8））；支持 * / N / A-B / A,B / */N；不支持秒级与 MON/@daily 宏`

先验一把语法（不落库）：

```js
const p = S.parseCron('0 9 * * 1-5');
console.log(p.ok, p.sets, p.text);            // sets = {minutes:[0],hours:[9],days:[...],months:[...],weekdays:[1,2,3,4,5]}
console.log(S.nextRuns({ kind:'cron', cron:'0 9 * * 1-5', tz:'Asia/Shanghai' }, { count: 5 }));
```

### 2.5 错过窗口怎么办：`miss_policy`

| 值 | 含义 | 什么时候选它 |
|---|---|---|
| `skip`（**默认**） | 错过的窗口**一个都不补**，只按策略记 `skipped_missed` | 绝大多数场景。理由是「静默放大代价」：一次补跑 3 个窗口=连建 3 个项目、烧 3 份额度 |
| `catchup` | **只补最近 1 个**错过窗口，更早的作废 | 停机几小时后想「至少跑最新的那一版」 |
| `catchup_all` | 补最近的 `catchup_max` 个（从最老的先跑，保证顺序） | 明确知道自己要连跑几版 |

配套字段：

| 字段 | 范围 / 默认 | 作用 |
|---|---|---|
| `catchup_max` | `0~50`，默认 `1` | `catchup_all` 单次最多补几个窗口；`0` 等于 `skip` |
| `grace_min` | `0~1440`，默认 `5` | **宽限**：到点后多少分钟内仍算「准点」而不是「错过」。tick 周期 60s、机器抖动、SQLite 写锁都可能让评估晚几秒，没有宽限会把准点误判成错过 |
| `skip_if_running` | `1`/`0`，默认 `1` | 上一个排产任务还没结束时**不叠跑**（本次窗口作废，记 `skipped_running`） |
| `catchup_after_pause` | `1`/`0`，默认 `0` | 恢复队列后是否补跑暂停期间错过的窗口。**默认不补**；只有它 `=1` 且 `miss_policy != 'skip'` 时才按策略补 |
| `budget_guard` | `1`/`0`，默认 `1` | 触发前是否过预算闸门（§4） |
| `retry_failed_max` | `0~10`，默认 `1` | 同一窗口因「建项目/入队失败」允许的额外重试次数 |
| `enabled` | 默认 `1` | 本条排产开关（§0.1） |

### 2.6 启停、改、删

```js
S.listSchedules({ enabled: 1, limit: 50 });     // 列表（limit 上限 200）；enabled 可传 1/0/'1'/'true'
S.getSchedule('S-0001');                        // 单条（带展示字段，见 §3.3）

// 暂停某条（不改水位线，重新启用时会重算）
S.updateSchedule('S-0001', { enabled: false }); // → { ...排产, changed:['enabled'], ignored:[], note:'未改动触发时间：水位线保持不变' }

// 改时间字段（kind/cron/at_time/weekdays/day_of_month/interval_minutes/once_at/tz/anchor_at）
// → 自动重算 next_run_at，note 会告诉你新的下次触发
S.updateSchedule('S-0001', { at_time: '07:30' });

// 保持水位线不变（只改展示/目标，或极端场景下不想动窗口）
S.updateSchedule('S-0001', { tz: 'UTC', keep_next_run_at: true });

// 改目标（换需求/换项目）
S.updateSchedule('S-0001', { target: { brief: '改成 5 集', spec: { episodes: 5 } } });

S.deleteSchedule('S-0001');                     // 默认删定义、**保留**触发历史（审计证据）
S.deleteSchedule('S-0001', { purge: true });    // 连 schedule_runs 一起删
```

- `updateSchedule` 返回里 `changed` 是真正改到的字段、`ignored` 是不认识的字段（不会静默吞掉，你能一眼看出自己写错了字段名）。
- `enabled` 由 `0 → 1` 时会**重算**水位线（避免停用 3 个月后沿用旧水位线、一启用就补跑一堆）。
- 停用期间 `next_run_at` 原样保留；`evaluateSchedule` 对停用条目的判定是 `record:false`（不写台账、不动水位线、`skip_count` 不增）。

### 2.7 让排产真正跑起来（定时器 + 单实例租约）

```js
const loop = S.startScheduler({ tickSeconds: 60 });   // 也可以用 tickMs: 60000
// console.log(loop.tickMs, loop.running, loop.state);
// …程序退出前：
loop.stop();
```

- `startScheduler({ tickMs, tickSeconds })` → `{ tickMs, running, state, tick, stop() }`；定时器 `.unref()`，不会拖住进程退出。
- **启动时会立刻跑一轮**（补齐停机期间错过的窗口，按 `miss_policy` 处理）——注意这一轮是真的会建项目/入队。
- **单实例租约**：一轮 tick（非干跑）会先 `acquireSchedulerLease({ owner })`，拿不到就整轮跳过并给出中文原因 `另一实例正在排产（本实例只读）：…`。租约存在 `app_config` 的 `scheduler:lease` 键，有效期默认 `180s`（`leaseTtlSeconds`，至少 30s）；进程崩溃后租约自然过期，不需要人工清理。
- 调试用：`readSchedulerLease(now)` 看当前租约（`held` 为 true 表示有效期内）、`tickSchedules({ dryRun: true })` 只判定不落库。
- **整机总开关**：配置文件里 `schedules.enabled=false`，或环境变量 `FACTORY_SCHEDULER=off`（环境变量优先）。关掉后 `tickSchedules` 返回 `reason:'排产已关闭（配置 schedules.enabled=false 或环境变量 FACTORY_SCHEDULER=off）'`。

配置文件（`config/config.json`，键名与 `schedulesConfig()` 合并，不必改代码）：

```jsonc
{
  "schedules": {
    "enabled": true,
    "tickSeconds": 30,        // 或 tickMs：两个都给时以 tickMs 为准
    "defaultTz": "Asia/Shanghai",
    "graceMin": 5,
    "catchup": false,         // 新建排产时未显式给 miss_policy 的默认来源：false → skip
    "maxCatchup": 1,          // 新建排产时 catchup_max 的默认值
    "skipIfRunning": true,
    "catchupAfterPause": false,
    "allowManualTick": true,
    "leaseTtlSeconds": 180
  }
}
```

## 3. 到点判定：这一轮到底跑没跑、为什么

### 3.1 权威水位线只有一根：`next_run_at`

| 时机 | `next_run_at` 怎么变 |
|---|---|
| 创建 | `nextOccurrence(s, after = now + 1s)`；`kind:'once'` 用 `once_at` |
| 触发成功（`fired`） | 从**本次窗口**继续向后算（不用 `now`，避免长 tick 跳掉中间窗口） |
| 被闸门拦下（`skipped_paused` / `skipped_budget` / `skipped_storage` / `skipped_running` / `skipped_production_cap`） | 同样推进（窗口「已用过」）。若保留，暂停 8 小时恢复后会瞬间涌入 8 个窗口的任务 |
| 按策略放弃（`skipped_missed`） | 从**最新到期窗口**向后再算一次 |
| `kind:'once'` 触发成功 | 置 `NULL` 且 `enabled=0` |
| 手动触发（`trigger:'manual'`） | **不动**（手动是「插队跑一次」，不消费自动窗口） |
| `PATCH` 改了时间字段 / `enabled` 0→1 | 重算（除 `keep_next_run_at:true`） |
| 改其他字段（`name`/`target`…） | 不动 |

判定只看 `next_run_at`，**不解析** `last_run_at` 反推。

### 3.2 判定码 → 中文含义（`reason_code`）

| `reason_code` | 界面中文（`SCHEDULE_REASON_TEXT`） | 落到台账的 `status` | 要不要管 |
|---|---|---|---|
| `due` | 到点触发 | `fired` | 正常 |
| `not_due` | 未到点 | —（不写库） | 正常 |
| `pending` | 处理中（预留行） | `failed` | 只有进程被杀才会留下，下一轮会按 `retry_failed_max` 重试 |
| `done_once` | 一次性排产已完成 | `fired` | 正常（本条已自动停用） |
| `skipped_disabled` | 排产已停用 | —（不写库） | 你按停了，正常 |
| `skipped_paused` | 队列暂停中 | `skipped` | 看 §7：先恢复队列 |
| `skipped_missed` | 错过窗口（按策略放弃） | `missed` | 看 §2.5：想补跑改 `miss_policy` |
| `skipped_running` | 上一次任务仍在执行 | `skipped` | 正常（不叠跑）；嫌慢可调 `skip_if_running` |
| `skipped_budget` | 月度预算闸门拦截 | `skipped` | 看 §4 |
| `skipped_production_cap` | 超过单次制片上限 | `skipped` | 看 §4 |
| `skipped_storage` | 磁盘超上限 | `skipped` | 清磁盘 |
| `skipped_no_target` | 目标制片项目不存在 | `skipped` | 只有 `existing_production` 会出；改 `target.productionId` 或删排产 |
| `skipped_deduped` | 窗口已处理（幂等去重） | `deduped` | 正常（并发/重复点击被拦下） |
| `error_trigger_failed` | 触发失败 | `failed` | 建项目/入队失败了，看 `last_error` |
| `error_invalid_time` | 时间字段非法 | `failed` | 表达式/时区坏了，改排产 |

`status` 是粗粒度 5 值（`fired` / `deduped` / `skipped` / `missed` / `failed`），`reason_code` 是细粒度；**审计和排错看 `reason_code`**。

### 3.3 一行一次判定：`schedule_runs`

每次「到点判定」都会在 `schedule_runs` 留一行（含中文 `reason`，能回答「昨晚 3 点为什么没跑」）：

```js
S.listScheduleRuns({ scheduleId: 'S-0001', limit: 20 });   // 也可按 status 过滤
// 每行含：window_key / trigger(auto|manual) / status / reason_code / reason(中文) /
//        attempts / miss_count / job_id / job_status / production_id / estimate / at
```

- **幂等**：唯一索引 `(schedule_id, window_key, trigger)` + `INSERT OR IGNORE`。并发 tick、进程重启、手动与自动撞车，同一窗口都只会产生一个任务。
- **为什么能这么硬**：触发时**先写一行 `failed/pending` 预留行，再建项目入队**，成功后改写成 `fired`。宁可留一条残行（下一轮按 `retry_failed_max` 重试，或你手动触发），也绝不重复花钱。
- **`window_key`**：自动=`occurrence`（秒级 UTC ISO）；手动=`manual:${触发时刻}` → **同一秒内重复点击只会触发一次**。
- **任务终态回写**：`reconcileScheduleRuns({ scheduleId, limit })` 把 `job_status` 同步成 `done/error/canceled`（`fired` 是「那一刻确实触发了」的事实，任务成败写在 `job_status`，二者不混）。取消的任务记 `failed` + 中文原因 `任务已取消（已完成的部分产物保留）`。

### 3.4 手动触发一次（插队）

```js
// 干跑：只返回判定结果，不落库、不建项目
await S.fireSchedule('S-0001', { trigger: 'manual', dryRun: true });

// 真跑：窗口 = 当前整秒；不推进自动水位线；仍受幂等与闸门约束
await S.fireSchedule('S-0001', { trigger: 'manual' });

// 暂停期间也要跑这一下？force 绕过闸门（暂停/存储/预算/上一轮在跑），但**绝不绕过幂等**
await S.fireSchedule('S-0001', { trigger: 'manual', force: true });
```

返回示例字段：`{ ok, fired, deduped, reasonCode, reason, runId, windowKey, occurrence, jobId, productionId, next_run_at, estimate }`。
同一秒再点一次会拿到 `{ fired:false, deduped:true, reasonCode:'skipped_deduped', reason:'该窗口已处理过（fired / due）：幂等去重，未重复触发' }`，**这是设计行为，不是 bug**（换一秒再点即可）。

### 3.5 未来几次触发长什么样

```js
S.nextRuns(s, { count: 5 });                   // [{ at, inMinutes, text }]
// text 例：'2025-06-02 09:00（Asia/Shanghai 周一）'
S.nextRunAt('S-0001');                         // 只取下一个 ISO 秒级时刻（算不出会抛错）
S.nextOccurrence(s, '2025-06-01T00:00:00Z');   // 纯函数：{ ok, at, scanned, error? }
S.scheduleSummary(s);                          // '每天 09:00（Asia/Shanghai） · 下次 2025-06-02 09:00'
```

## 4. 排产 × 队列暂停 × 预算：五道闸门

排产触发前的闸门顺序是**固定的**，依次为：**队列暂停 → 全局预算自动暂停 → 存储 → 月度预算 → 单次制片上限**。
理由：暂停是人的意志（最先看），全局预算是「整座工厂该不该停」，存储是硬约束（磁盘满了跑什么都白跑），最后两级才轮到「这一次该不该花钱」（先看全局再看单次）。

| 级别 | 判定依据 | 命中后 |
|---|---|---|
| ① 队列暂停 | `pauseState().paused` | 不建项目、不入队，记 `skipped_paused`；**不会自动恢复队列** |
| ② 全局预算/额度 | `shouldAutoPause({ images, videos })` | 命中即调 `pauseQueues({ by:'system' })` 暂停整个队列（进 `jobs:pause-log`，决策时间线可见），本次记 `skipped_budget` |
| ③ 磁盘 | `checkStorage()` | 记 `skipped_storage` |
| ④ 月度预算 | `checkBudget({ images, videos })` | 记 `skipped_budget` |
| ⑤ 单次制片上限 | `checkProductionBudget({ amount })` | 记 `skipped_production_cap` |

排产侧的估算**复用** `estimateProduction({ spec })`，并把关键数字（`amount` / `keyframeCalls` / `videoCalls` / `costLevel`…）写进 `schedule_runs.estimate`，方便事后审「当时预计花多少」。

**诚实说明**：月度上限只覆盖**图 / 视频 / 配音**三项计费（台账字段 `images` / `videos` / `ttsChars`，单价格 `budget.imageUnit` / `videoUnit` / `ttsPerKChars`，上限 `budget.monthlyCap`）。**LLM token 不进台账**，所以免费阶段（`brief`/`cast`/`novel`/`script`/`canvas`）的 token 花费不受月度上限约束 —— 不要把「有预算闸门」理解成「一定不超支」。另外 `budget.monthlyCap` / `productionCap` 默认 `0` = 不限，或把预算保护关掉时，月度闸门会直接放行并给出原因 `未启用预算保护（设置 → 数据与预算）`。

### 暂停 × 排产的五种组合

| 场景 | 排产行为 | 记录 | 恢复队列后 |
|---|---|---|---|
| 未暂停、本条 `enabled=1` | 正常触发 | `fired` / `due` | — |
| **队列暂停** | 不建 job、不建项目 | `skipped` / `skipped_paused` + 中文原因（含暂停原因摘录） | 默认**不补跑**（窗口作废）；仅当 `catchup_after_pause=1` 且 `miss_policy != 'skip'` 才按策略补 |
| 本条 `enabled=0` | 不触发，水位线不动 | `skipped` / `skipped_disabled`（不写库、`skip_count` 不增） | 重新启用时按 §3.1 重算水位线 |
| 上一个排产任务还在跑 | `skip_if_running=1` → 本次不叠跑 | `skipped` / `skipped_running` | 下一个窗口自然来 |
| 磁盘/预算超限 | 不触发 | `skipped` / `skipped_storage` / `skipped_budget` / `skipped_production_cap` | 处理完再看下一窗口 |

补充两条：

- **手动触发在暂停期间也会被拦**（记 `skipped_paused`）；确实要跑就用 `force:true`，或先恢复队列。
- **双保险**：排产建的任务是普通 `studio` 任务（`type:'studio', limit:1`），队列自己的暂停检查是第二道闸门——即使排产判定漏判，任务也不会真的开跑。

## 5. 阶段失败自愈：换了什么、为什么、影响

模块：`src/self-heal.js`。它**只做「判定 + 中文文案 + 记账回调」**，绝不自己发起生成调用 —— 真实的「跑一次」由集成方以 `run(backend, info)` 注入，所以行为完全可离线复现。

### 5.1 四步走（顺序不可调换）

1. **分类**：错误归到 11 类之一（复用 `src/retry.js` 的 `ERROR_KINDS` / `classifyError`，不另造分类名）。
2. **同后端重试一次**：只对 `rate` / `server` / `network`（`RETRYABLE_HEAL_KINDS`）。退避由既有 `withRetry` 负责，这里只补**一次**外层调用。
3. **换后端一次**：沿**单向**降级链 `comfyui-h3 → generic-http → placeholder` 往后走，永不反向（「升到更贵/更真」一律交人）。
4. **先告知、再执行**：换之前必须先写成非空的中文告知（`notice`）；写不进去就**放弃切换**并抛中文错误 `未能写入降级告知记录，已放弃切换后端（禁止静默换后端）`，且**零生成调用**。账本里没有记录，就不可能发生过生成。

调用预算（`MAX_GENERATE_CALLS_PER_SHOT = 3`）：

| 错误类型 | 首发 | 同后端重试 | 换后端后 | 合计 |
|---|---|---|---|---|
| `rate` / `server` / `network` | 1 | 1 | 1 | **3** |
| `timeout`（原实例探测失败）/ `config` / `format`（受限） | 1 | 0 | 1 | **2** |
| `auth` / `quota` / `moderation` / `client` / `unknown` | 1 | 0 | 0 | **1** |

超了就 `action:'stop'`，如实失败（不靠叠加调用硬跑）。

### 5.2 哪些错误能自愈（12 类对照表）

> 本表与代码一一对应：`src/self-heal.js:202-231` 的 `HEAL_BY_KIND`（注释里就写着「12 类错误 → 故障归属 / 是否可自愈 / 动作 / 中文建议」）。**`model` 一行是本轮补上的**（此前 `model` 没有档案，会落到 `unknown` 兜底，用户只看到「未知错误」）。

| `errorKind` | 中文标签 | 故障归属 | 可自愈 | 动作 | 对它的处理 |
|---|---|---|---|---|---|
| `rate` | 触发限流（429） | `instance` | ✅ | `retry-same` → 仍失败 `degrade` | 先退避重试，再换后端 |
| `server` | 服务端错误（5xx） | `instance` | ✅ | `retry-same` → 仍失败 `degrade` | 同上（实例整体挂了就走降级链） |
| `network` | 网络异常（连接失败/被重置） | `instance` | ✅ | `retry-same` → 仍失败 `degrade` | 同上 |
| `timeout` | 请求超时 | `instance` | ⚠️ 有条件 | `degrade`（仅探测失败时） | **先探原实例**：活着 → 不换（可能只是排队/慢镜，且生成类接口可能已在服务端跑完并计费） |
| `config` | 本地配置缺失或非法 | `local-config` | ⚠️ 默认否 | `hold-human` | 默认不换（避免换个厂商继续对不上）；仅当显式 `allowLimitedSwitch:true` 才允许换到已配置且探测通过的下一跳 |
| `format` | 响应结构不符合配置的字段路径 | `local-config` | ⚠️ 默认否 | `hold-human` | 同上（先核对 `responseVideoPath` / `fieldMap`） |
| `auth` | 鉴权失败（Key 无效或未授权） | `account` | ❌ | `hold-human` | 换后端解决不了：更新 Key 或换实例地址后重跑 |
| `quota` | 额度/余额不足（需充值或提额） | `account` | ❌ | `hold-human` | 充值 / 清零台账；**显式 `retry:false`（不自动重试）**；「降级到免费占位」只能人工点 |
| **`model`** | **模型不可用（模型名错误 / 未开通 / 已下线）** | **`params`** | ❌ | `hold-human` | **换后端救不了**（下家未必有这个模型）、**不重试**（同参数重试必然同样失败且可能重复计费）。排查：核对模型名与开通状态，或改用其他模型后重跑；`node scripts/check-backends.js` 可看各后端模型是否可用/已开通（`src/self-heal.js:218-226`） |
| `moderation` | 内容审核不通过 | `content` | ❌ **红线** | `hold-human` | **任何配置都改不了**：改提示词/画面或人工复核这一镜 |
| `client` | 请求参数被厂商拒绝（4xx） | `params` | ❌ | `hold-human` | 核对模板字段映射与参数范围（比例/时长/分辨率） |
| `unknown` | 未知错误 | `unknown` | ❌ | `hold-human` | 不猜、不硬跑，按报错原文排查后再决定 |

一句话：**实例侧**（限流/5xx/网络/超时-探测失败）可自愈；**账号侧**（`auth`/`quota`）、**请求侧**（`model`/`client`）、**内容侧**（`moderation`）、**未知**（`unknown`）一律不可自愈，交人工。

> **与 `src/retry.js` 的口径一致性**：`quota`、`auth`、`model` 三类在两边都是「**永不重试**」的红线 —— `src/retry.js` 的可重试清单 `RETRY_KINDS` 只含 `rate`/`server`/`network`（`src/retry.js:85`、`:90`），`src/self-heal.js` 的 `NO_SWITCH_KINDS` 把它们列入「永不换后端」（`src/self-heal.js:59-61`）。

### 5.3 降级链与四种模式

```text
comfyui-h3  ──跳1──▶  generic-http  ──跳2──▶  placeholder  ──▶（终点，无下一跳）
   付费                  付费                    免费
真实视频生成          真实视频生成            「有运动的关键帧」（非真实视频）
```

`DEGRADE_CHAIN = { 'comfyui-h3': ['generic-http','placeholder'], 'generic-http': ['placeholder'], 'placeholder': [] }`
`PAID_BACKENDS = ['comfyui-h3','generic-http']`、`FREE_BACKENDS = ['placeholder']`。

| 模式（`SELFHEAL_MODES`） | 含义 | 允许换后端 |
|---|---|---|
| `off` | 完全关闭：不重试、不换 | ❌ |
| `report` | 只报告不换：给建议、阶段标失败 | ❌ |
| `auto-free`（**默认**） | 允许自动 `→placeholder`（免费）；付费跳仍需人工批准 | ⚠️ 仅免费跳 |
| `allow-paid` | 额外允许 `comfyui-h3 → generic-http`，但**仍须人工批准**（`requiresApproval:true`，不会自动执行） | ✅ 免费跳 + 已批准的付费跳 |

策略从 `config/config.json` 的 `video.selfHeal` 读，用 `healPolicy()` 归一化（非法 `mode` 回落到 `auto-free`）：

```jsonc
{
  "video": {
    "selfHeal": {
      "mode": "auto-free",          // off | report | auto-free | allow-paid
      "maxSameBackendRetry": 1,     // 「重试一次」
      "maxSwitchesPerScope": 1,     // 同一 scope 只换一次（I5）
      "maxGenerateCallsPerShot": 3, // 首发 + 重试一次 + 换后端一次
      "tripThreshold": 3,           // 连续 3 个同类可自愈错误 → 阶段级熔断判定
      "lockEpisodeBackend": true,   // 一集内一致性锁定
      "allowFreeFallback": true,    // 允许 → placeholder
      "allowPaidSwitch": false,     // 允许付费跳（仍须人工批准）
      "requireProbe": true,         // 有探测证据时目标必须 ok!==false
      "degradedRatioAlert": 0.3,    // 同集降级比例告警阈值（供集成线 pauseQueues）
      "requireRecord": false        // true=必须落账成功才允许换（I1 严格档）
    }
  }
}
```

```js

import { loadConfig } from './src/config.js';

```

**建议改用 `report` 的场景**：要做出海/商用交付、该镜已 `picked=1`（有人工采用版本）、本次是质检/交付阶段的重跑、或月度预算已用超 80%。

**换后端前的四个前置条件**（缺一不换，拦下时结果里会给 `blockedBy`）：

| 编号 | 条件 | 实现位置 |
|---|---|---|
| C1 | **目标可用**：有探测证据时目标必须 `ok !== false`（`probes` / `probeOf` / `probes` 映射）；严格档 `requireProbe:true` 时「没有证据」也不许换 | `fallbackChain({ from, used, allow, probes })` / `nextBackend()` |
| C2 | **能力够用**：逐项对齐（首帧、尾帧、音轨、真实视频、单镜时长、画幅比例） | `canDegradeTo({ to, facts, need })` |
| C3 | **闸门放行**：队列未暂停（`paused:false`）且预算/取消等闸门通过；命中 → `action:'stop'`、`blockedBy:'C3'` | `decideHeal` 的 `paused` / `gate` 入参 |
| C4 | **账本可写**：注入的 `record(event)` 必须返回事件号；抛错或拿不到 id → **放弃切换并抛中文错误**（不是返回值，是硬失败） | `runWithHeal` |

能力事实表（`BACKEND_CAPABILITIES`，判定 C2 用的就是它）：

| 能力 | `comfyui-h3` | `generic-http` | `placeholder` |
|---|---|---|---|
| 真实视频生成 | ✅ | ✅ | ❌ 仅关键帧运镜 |
| 首帧驱动 | ✅ | ⚠️ 视模板占位符 | ⚠️ **必须已有可用关键帧** |
| 尾帧过渡 | ⚠️ 视节点映射 | ⚠️ 模板需含末帧占位符 | ✅ 降级为**交叉溶解 xfade** |
| 自带音轨 | ✅ | ❌ | ❌ |
| 出片速度 | 45s~120s/条 | 视厂商 | ≈1.4s/条（本地 ffmpeg） |
| 计费 | 付费（记 `videos+1`） | 付费（记 `videos+1`） | 免费 |
| 本地可复现 | 中 | 低 | 高 |

> 口径提醒：`placeholder` **不是**真实视频生成，只是「有运动的关键帧」。`→ placeholder` 属**画质级降级**，必须照 `notice` 人工复看，绝不能当成「换了台机器重跑」。

### 5.4 怎么知道「它换了」

三条互补的路子：

1. **结果字段**（`runWithHeal` / `decideHeal` / `planSelfHeal` 的返回值）：

   | 字段 | 含义 |
   |---|---|
   | `action` | `retry-same` / `degrade` / `hold-human` / `stop`（`HEAL_ACTIONS`） |
   | `degraded` / `healed` | 是否**真的**换了后端（`false` = 只重试过或只报告） |
   | `from` / `to` | 原后端 / 目标后端（`to` 在未换时为空） |
   | `attempts` / `calls` / `retried` / `switches` | 调用与重试/切换计数（`calls` 是本次真实发生的生成调用次数） |
   | `chainIndex` | 走到降级链第几跳（`0` 未换、`1` 跳1、`2` 跳2） |
   | `blockedBy` | 被哪个前置条件拦下：`C1` / `C2` / `C3`（未拦下为 `null`） |
   | `requiresApproval` | 目标是付费后端 → `true`（方案已备好，等你批准，**未执行**） |
   | `needsHumanReview` | 换过后恒为 `true`（降级产物必须人工复看） |
   | `eventId` | 账本事件号（`SH-xxxx`），会写进告知文案 |
   | `notice` | 中文告知（**非空**），见下 |
   | `lostCapabilities` / `keptCapabilities` / `costImpact` / `consistency` | 损失 / 保留 / 费用口径 / 一致性说明 |
   | `errorKind` / `errorLabel` / `errorExcerpt` | 错误分类、中文标签、报错原文前 200 字（不吞原文） |

2. **告知文案**（`describeHeal(rec)`，别名 `degradeNotice`；全库唯一实现，别在别处重写文案）。三种形态，实际输出长这样：

```text

损失：真实视频生成（物理运动）、自带音轨。
保留：首帧驱动（必须已有可用关键帧）、关键帧一致性、首尾帧过渡（降级为交叉溶解 xfade）、本地可复现（纯本地 ffmpeg，不走外网）。
费用：本条由真实视频后端 comfyui-h3（付费，已记 1 条用量）降级为本地免费运镜 placeholder，后续镜头不再计费。
一致性：本镜自本次起改用 placeholder，本集剩余镜头沿用同一后端，前后画风/音轨可能不一致，请人工复看。
请人工复看后再交付（事件 SH-2f1c9a）。
```

### 5.5 影响：损失了什么、花了多少钱、要不要人工复看

- **能力损失**：`degradationOf({ from, to })` 给出中文能力名。例：`comfyui-h3 → placeholder` 丢「真实视频生成（物理运动）」「自带音轨」，换到「首尾帧过渡（降级为交叉溶解 xfade）」。
- **费用**：`costImpact` = `{ from:'paid'|'free', to, currency:'CNY', unit:'视频条数', note, usageRecorded }`。要点：
  - 付费 → 免费：**本条**已记 1 条用量，**后续镜头不再计费**；
  - 付费 → 付费：换供应商会**再记 1 条**用量 → 所以 `allowPaidSwitch` 默认 `false`，且仍需人工批准；
  - 免费 → 免费：不产生费用。
- **一致性**（`consistencyOf()`）：同集内一旦降级，`lockEpisodeBackend:true` 时给出的口径是「本集剩余镜头一律沿用新后端」，`consistency.note` 会明确写「本集自第 N 镜起改用 X，前后画风/音轨可能不一致，请人工复看」（这是模块给出的口径与文案，真正让剩余镜头沿用同一后端由集成线执行）。
- **必须人工复看**：`needsHumanReview` 换过后恒为 `true`。降级产物不是「等价替换」。
- **一集别悄悄做成占位片**：`degradedRatioAlert`（默认 `0.3`）与 `shouldTripStageDegrade({ consecutive, threshold })`（连续 3 个同类可自愈错误 → 阶段级熔断判定）是给集成线用的口径 —— 命中后应调 `pauseQueues({ by:'system' })` 暂停队列并中文告警。

## 6. 不自愈的错误：请先修配置，别等它自己好

| 现象 / 报错关键字 | `errorKind` | 你该做什么 |
|---|---|---|
| `401` / `403` + `unauthorized` / `invalid api key` / 鉴权失败，且**文案里没有额度或模型关键词** | `auth` | 更新 Key 或换实例地址，然后重跑该阶段（例：`AccessDenied` 这类无权限） |
| `arrearage` / `accountoverdue` / `insufficient` / `balance` / `billing` / `quota` / `resource not granted` / `欠费` / `额度` / `余额` / `配额`（**即使包在 403 里**） | `quota` | 充值或清零台账；要省钱就用**人工**把该阶段改成免费后端（系统不会自动换，也**不会自动重试**） |
| `model_not_found` / `ModelNotOpen` / `model does not exist` / `has not activated the model` / `no available channel for model` / `InvalidEndpointOrModel.NotFound` / `模型不存在` / `模型未开通` / `模型已下线`（**即使包在 503 里**） | `model` | 核对模型名与开通状态，或改用其他模型后重跑；`node scripts/check-backends.js` 可看各后端模型是否可用/已开通。**不会自动重试、也不会换后端**（换后端救不了「模型不存在」，重试必然同样失败） |
| `moderation` / `content policy` / `审查` / `违规` / `敏感` | `moderation` | **改提示词/画面内容**再跑，或人工复核这一镜。换后端 = 试图绕过审核，红线禁止 |
| `4xx` 参数被拒 | `client` | 核对模板字段映射、比例/时长/分辨率取值范围 |
| 响应里 `找不到字段 xxx` / 返回非 JSON | `format` | 核对 `responseVideoPath` / `fieldMap`（默认不换后端） |
| `未配置` / `未启用` / `请先` / `缺少 path` | `config` | 到设置页补齐该后端配置（例：`未配置通用视频接口 URL（设置 → 视频后端）`） |
| `超时` / `timeout`，但原实例探测**在线** | `timeout` | 默认**不换**（可能只是排队/慢镜，且服务端可能已跑完并计费）。延长等待或人工处理 |
| 兜底 `unknown` | `unknown` | 不猜不硬跑：按报错原文排查（工作流/模板与实例是否匹配、参数是否越界） |

> **本轮修正（别再按旧版判断）**：错误归类现在**先判文本关键词、状态码只在文本判不出来时兜底**（`src/retry.js:25-43`、`:54-62`），所以「**403 的欠费**」不再显示成鉴权失败（归 `quota`），「**503 里的模型不存在**」也不再被判成可重试的 5xx（归 `model`，不重试）。仍然归 `auth` 的是「**有 401/403 且文案里没有额度/模型关键词**」的情形（例如 `AccessDenied` 无权限）。
> **红线**：`model` 的关键词一律锚定在 `model`/`endpoint` 前缀或完整短语上，**裸 `not found` / 裸 `invalid` 刻意不收** —— 否则 `404 Not Found`（资源不存在）与 `InvalidParameter.*`（参数校验失败）会被误判成模型不可用（`src/retry.js:29-33`，逐条确证见 `strategist/runs/RETRY-MODELWORDS.json`）。

## 7. 恢复暂停的队列（以及它跟排产的关系）

队列暂停状态存在 `app_config` 的 `jobs:paused` 键里，**重启后依然暂停**（避免「重启一下就把闸门绕过去」）；暂停/恢复历史在 `jobs:pause-log`。

### 7.1 三种恢复方式

| 方式 | 怎么做 | 说明 |
|---|---|---|
| **界面（最省事）** | 看顶部徽章 `⏸ 队列已暂停 · 点击恢复`（中间会标出是 `人工` 还是 `预算/额度`），点一下即可 | 徽章 tooltip 会显示暂停原因与「排队中 N 个任务（未丢失）」；恢复成功会刷新页面 |
| **HTTP** | `POST /api/queue/resume`，body `{ "by": "human", "note": "已充值" }` | 同页还有 `GET /api/queue/state`（看 `paused` / `reason` / `by` / `stats` / `usage` / `history`）与 `POST /api/queue/pause`（人工暂停，body `{ reason, by }`） |
| **Node API** | `resumeQueues({ by:'human', note:'已充值' })` | 返回 `{ ok:true, paused:false, resumedFrom:'月度预算已达上限' }`，并把该类型队列重新泵一遍 |

```js
import { pauseState, pauseHistory, pauseQueues, resumeQueues } from './src/jobs.js';
pauseState();                                   // { paused:true, reason:'…', at:'…', by:'system', scope:'all' } 或 { paused:false }
pauseHistory(10);                               // 最近 10 条暂停/恢复历史（决策时间线也用它）
pauseQueues({ reason:'人工暂停：要改分镜', by:'human' });   // → { ok, paused, reason, by, at, queued, running }
resumeQueues({ by:'human', note:'改完了' });
```

### 7.2 恢复之后会发生什么（这是最容易被误解的一点）

- **已经在跑的任务跑完，排队的任务继续泵**（暂停不丢任务、不标失败）。
- **排产不会自动补跑暂停期间错过的窗口**：那些窗口在暂停时已被记成 `skipped_paused` 并推进了水位线；恢复后从**下一个**窗口继续。
- 想让它在恢复后按策略补跑，需要同时满足两条：`catchup_after_pause = 1` **且** `miss_policy != 'skip'`。
- **排产永不自动恢复队列**：恢复是人的决定（预算是否已放开只有你知道）。
- 想知道「昨晚为什么没跑」：`listScheduleRuns({ scheduleId })` 里找 `skipped_paused` 那几行，中文原因里带着当时的暂停理由。

## 8. 常见问题排查

### 8.1 创建排产时报错

| 报错（原文） | 原因 | 处理 |
|---|---|---|
| `排产名称必填（≤60 字）` | `name` 空 | 起个名字 |
| `排产名称已重复：xxx（已存在 S-0002…）` | 名字撞了 | 换名字或先改那条 |
| `kind 非法：xx（可选 once/interval/daily/weekly/monthly/cron）` | `kind` 拼错 | 对照 §2.3 |
| `interval 间隔必须是 1~10080 的整数分钟` | 少填/超范围/带小数 | 改整数分钟 |
| `at_time 必须是 'HH:MM'（24 小时制），例如 '09:30'` | 写成 `9:00`/`9点` | 补零成 `09:00` |
| `weekdays 必须是 0~6（0=周日）的列表，例如 '1,3,5'` | `weekly` 没给/越界 | `'1,3,5'` |
| `day_of_month 必须是 1~31…` | `monthly` 没给/越界 | 给 `1~31` |
| `once_at 必须是 'YYYY-MM-DD HH:MM'（按 tz 解释）且晚于当前时刻` | 格式错或时间已过 | 改成将来的墙钟时刻 |
| `cron 表达式非法：…` | 段数/范围/名称宏 | 对照 §2.4 |
| `无效时区：Bad/Zone（请用 IANA 名称…）` | `tz` 不是 IANA 名 | 用 `Asia/Shanghai` / `UTC` 等 |
| `mode=existing_production 时必须给 target.productionId，且该制片项目必须存在` | 项目 id 缺/不存在 | 补上或改成 `new_production` |
| `请给 target.brief（一句话需求）或 target.spec（制片参数）` | `target` 空 | 至少给 `brief` 或 `spec` |
| `miss_policy 非法：xx（可选 skip/catchup/catchup_all）` | 拼错 | 对照 §2.5 |
| `按当前表达式算不出未来的触发时刻（请检查 cron / once_at）` | 表达式永远不匹配（如 2 月 30 日） | 换表达式；**不会留下半成品** |

### 8.2 「到点了但没跑」，按这个顺序查

1. **看队列暂停没**：`pauseState()` / `GET /api/queue/state`。暂停中 → 排产只记 `skipped_paused`（§7）。
2. **看本条 `enabled`**：`listSchedules()` 里该条目 `enabled=0` → 你在停用它（水位线保留，不写台账）。
3. **看 `listScheduleRuns({ scheduleId })` 的中文 `reason`**：它会直接说清是「队列暂停中」「已错过 N 个窗口」「上一次任务仍在执行」还是「月度预算闸门拦截」。
4. **对照时间与宽限**：`grace_min` 默认 5 分钟。tick 超过宽限才到 → 按 `miss_policy` 处理（默认 `skip` = 错过就错过）。
5. **看 tick 有没有在跑**：`readSchedulerLease()` 的 `held`；若原因是 `另一实例正在排产（本实例只读）`，说明另一个进程/实例持有租约。`tickSchedules({ dryRun:true })` 能看到「此刻哪些排产到点了、判定码是什么」，且不落库。
6. **总开关**：配置文件 `schedules.enabled=false`，或环境变量 `FACTORY_SCHEDULER=off` → 整轮跳过。

### 8.3 其他常见疑问

| 疑问 | 答案 |
|---|---|
| 手动触发点了没反应 | 同一秒内重复触发会被幂等拦下（`windowKey = manual:<整秒>`），返回 `skipped_deduped`；换一秒再点。暂停期间手动触发也会被拦，除非 `force:true` |
| 一次性排产跑完为什么自己停了 | 设计如此：`kind:'once'` 触发成功后 `enabled=0`、`next_run_at=NULL`，台账记 `done_once` |
| 会不会重复跑同一窗口 | 不会。唯一索引 `(schedule_id, window_key, trigger)` + 先写预留行再建任务；手动与自动也互不顶掉 |
| 重启会不会把错过的窗口全补跑 | 不会（默认 `skip`）。重启后 `startScheduler()` 立刻跑一轮，只按 `miss_policy` 处理 |
| 进程被杀在「建项目」中间会怎样 | 台账留一行 `failed/pending`，下一轮 tick 看到 `failed` 且 `attempts < 1 + retry_failed_max` 时**重试同一窗口**；窗口不会被悄悄丢掉 |
| 任务被取消/失败后排产状态是什么 | `reconcileScheduleRuns()` 把 `job_status` 写成 `canceled/error`，并把 `schedules.last_status` 记 `failed` + 中文 `last_error` |
| 排产任务在队列里长什么样 | 标题 `[排产] <排产名>`，`type:'studio'`、`limit:1`，与人工任务同队列同闸门 |
| 想直接看库 | 表 `schedules`（定义 + 水位线 + 计数）与 `schedule_runs`（一行一次判定，含中文原因与 `estimate`）。`DELETE` 排产默认保留 `schedule_runs`（审计），`purge:true` 才一起删 |
| 自愈会不会偷偷花我的钱 | 不会：付费目标后端一律 `requiresApproval:true` 且不自动执行；换后端前必须先写非空中文告知，写不进去就放弃切换（零生成调用） |
| 自愈最多折腾几次 | 单镜最多 3 次生成调用（首发 + 同后端重试一次 + 换后端后一次）；同一 `(scope, scope_id, stage, from)` 只允许换一次（`maxSwitchesPerScope:1`），超了 `hold-human` 交人工 |

## 附：接口约定（实测，来源 `scripts/accept-schedules.sh` 的 14 项验收）

> 这两条是写验收脚本时被服务端的中文报错「教」出来的，容易踩，先记下来。

1. **排产是「定时建制片项目」，不是定时跑命令**
   `POST /api/schedules` 必须带 `target`：
   - `target.brief`（一句话需求）或 `target.spec`（制片参数）二选一，否则返回
     `请给 target.brief（一句话需求）或 target.spec（制片参数）`。
   - 想只想登记不跑：`"enabled": false`（默认停用，避免建完就触发）。

2. **间隔字段名是 `interval_minutes`（不是 `every_minutes`）**
   - 取值 **1~10080** 整数分钟；写错会返回 `interval 间隔必须是 1~10080 的整数分钟`。
   - 例：
     ```bash
     curl -s -X POST http://127.0.0.1:8788/api/schedules \
       -H 'content-type: application/json' \
       -d '{"name":"每晚 21:00 出片","kind":"interval","interval_minutes":1440,
            "miss_policy":"skip","enabled":false,
            "target":{"brief":"拍一部一集的雾港悬疑短剧，每集 30 秒"}}'
     ```

3. **一键自检（不改动你的数据）**
   ```bash
   bash scripts/accept-schedules.sh        # 默认在 8901 起临时实例，14 项检查，跑完自动清理
   ```
   脚本会额外取证「真实 `config/config.json` 跑前跑后 md5 一致」，因此可以放心随时运行。

4. **队列暂停与排产的联动**：队列处于暂停态时排产不会推进（返回不 fire），需先
   `POST /api/queue/resume` 恢复；暂停原因与历史可在 `GET /api/queue/state` 查看，也会出现在制片 Agent 页的「🧭 决策时间线」里。
