## 一、先明确一个依赖关系（重要）

P3 能在"每侧单输入"语义下独立落地，但 **P5 的成片节点天然需要多片段有序**：

| 需求 | 依赖 |
|------|------|
| 一个 timeline 节点接收 N 个镜头片段 | 需要 `slot` 决定**拼接顺序** |
| 没有 `slot` 会怎样 | 拼接顺序 = 数据库返回顺序（`canvas_links` 无排序保证），**成片镜头顺序会随机错乱** |

**结论：P5 必须等 P2 的 `slot` 落地**（或退化为 `data.order` 显式数组，见第四节备选方案）。
这不是可以"先凑合"的地方——短剧成片顺序错乱是致命缺陷，且**不会报错，只会静默产出错片**。

## 三、节点类型设计（三个，职责分离）

| 节点 | 职责 | 输入 | 输出 |
|------|------|------|------|
| `shot` | **一集分镜容器**：展开 N 个镜头槽，是"编排视图" | — | `clip`（N 路，按镜头序） |
| `timeline` | **成片包装**：按序拼接 + 字幕 + 音轨 + 淡入淡出 | `clip` × N（**按 slot 排序**） | `film` |
| `output` | **交付终点**（P3 已定义）：标记交付物、导出 | 任意 | — |

与 P3 的分工：
- P3 的 `output` 节点执行 **`assembleVideos`**（裸拼接，无包装）——保持简单
- P5 新增 `timeline` 节点执行 **`finishEpisode`**（完整包装）

> 若嫌两个类型冗余，可合并为 `output` + `data.finish` 配置开关；但**建议分离**——裸拼接与带包装成片的失败原因与耗时完全不同，UI 与审计上都更清晰。

## 四、步骤 1 · 端口扩展（P2 的 `NODE_KINDS` / `PORT_RULES` 补两项）

```js
  shot:     { in: [],                                   out: ['clip'] },
  timeline: { in: ['clip1', 'clip2', 'clip3', 'clip4', 'clip5', 'clip6',
                   'clip7', 'clip8', 'clip9', 'clip10'], out: ['film'] },
  output:   { in: ['in'],                               out: [] },
```

端口兼容表补：`clip: ['clip1'..'clip10', 'in', 'timeline']`
（P4 的 `timeline` 名称若已占用，改名为 `clip_in` 等，保持全局唯一。）

**槽位语义**：`clip1..clip10` 的序号**即拼接顺序**，与 P2 的 `slot` 双重表达——
- `to_port` 决定"第几段"（语义）
- `slot` 决定"同端口多入边时的次序"（兜底）

**渲染时的顺序解析（必须明确，否则静默错片）**：

```js
/** 解析 timeline 节点的片段顺序：优先 clip1..N 端口号，其次 slot，最后创建时间 */
export function orderedClips(links, valueOf) {
  const ins = links.filter((l) => l.to_node === timelineNodeId);
  const withKey = ins.map((l) => ({
    link: l,
    file: valueOf(l.from_node),
    portIdx: /^clip(\d+)$/.test(l.to_port || '') ? Number(l.to_port.match(/^clip(\d+)$/)[1]) : 999,
    slot: l.slot ?? 0,
  })).filter((x) => x.file);
  withKey.sort((a, b) => (a.portIdx - b.portIdx) || (a.slot - b.slot)
    || String(a.link.created_at || '').localeCompare(String(b.link.created_at || '')));
  return withKey.map((x) => x.file);
}
```

**备选（P2 推迟时）**：`timeline` 节点 `data.order = [nodeId, nodeId, …]` 显式数组，执行时按数组下标解析。
**代价**：顺序不再由画布连线表达，Agent/人类都可能与画布脱节。**仅作降级方案。**

## 六、步骤 3 · `shot` 节点的"一键铺开"（可选，但体验提升明显）

`shot` 节点 = 一集分镜的编排视图。提供两个操作（HTTP + MCP 各暴露一个）：

```js
/**
 * 把一集的分镜铺成画布：建 shot 节点 + N 个 video 节点 + N 条 clip 连线
 * 不发起任何生成调用（符合 P4 闸门原则）
 */
export function spreadEpisodeToCanvas({ canvasId = 'CV-MAIN', scriptId, code, cols = 4 } = {}) {
  const ep = get('SELECT * FROM script_episodes WHERE script_id = ? AND code = ?', scriptId, code);
  if (!ep) throw new Error(`未找到分集：${code}`);
  const shots = all('SELECT * FROM shots WHERE episode_id = ? ORDER BY idx ASC', ep.id);
  if (!shots.length) throw new Error(`分集 ${code} 还没有分镜，请先生成分镜`);
  // 1) 建 shot 容器节点
  // 2) 每个镜头建一个 video 节点（data.shotId / data.duration / data.prompt 取自镜头）
  // 3) 建 clip{i} 连线（顺序 = shots.idx）
  // 4) 建一个 timeline 节点并接入全部 clip{i}
  return { shotNodeId, videoNodeIds, timelineNodeId, clipCount: shots.length };
}
```

**关键**：此函数**只改数据、不生成**。生成仍走 P4 的 `canvas_plan` → 确认码 → `canvas_run` 链路。
这样"铺开一张 100 镜的图"变成可审阅、可分批、可单点重跑的形态——正是 LibTV 的用法。

## 八、兼容性红线

1. **不得重写拼接/字幕/音轨逻辑**——一律经 `finishEpisode`；`assembleVideos` 只用于 `output` 节点的裸拼接。
2. **顺序必须在有 `slot` 之后才允许上生产**；P2 未落地时只能用 `data.order` 降级，且**必须在 UI 上显著提示"顺序由节点参数指定，移动连线不会改变成片顺序"**。
3. **静默错片是本次改造最危险的失败模式**：`timeline` 执行前必须校验 `clips.length === 连入的 clip 端口数`，不一致时**直接报错**，不得"能拼几段算几段"。
4. 字幕台词优先复用模块 3 的既有推断，**不要**在画布侧另写一套说话人推断。**实测可见性**：
   - ✅ `inferSpeaker(shot, nameById)` **已导出**（`src/modules/render.js:199`）→ P5 可直接 import
   - ❌ `isVoiceOver(action)` 是**模块私有**的 const 箭头函数（`src/modules/render.js:212`，正则 `/画外音|旁白|内心/`），P5 无法 import
   - **推荐做法**：在 `render.js` 里加一个导出的小 helper（**唯一的既有文件改动，仅新增一个 export**），并让既有 `clipsForEpisode` 改调它，保证两处逻辑只有一份：
     ```js
     /** 镜头 → 字幕台词（画外音不当作台词）—— 供模块4 与画布 timeline 节点共用 */
     export function dialogueOfShot(shot, nameById = new Map()) {
       if (isVoiceOver(shot?.action)) return '';
       return inferSpeaker(shot, nameById)?.text || '';
     }
     ```
   - **降级方案**（**当前建议默认走这条**）：`src/modules/render.js` 正在被并行会话实时修改（`05ae3e23` → `066c7391`，发生在 18:53→19:05 之间），
     此时**不要**去动它。改为 P5 直接 import 已导出的 `inferSpeaker`，并对画外音判断**内联同一正则**。
     **必须在代码注释里标明"与 `src/modules/render.js:212` 保持同步"**，否则两处正则日后必然漂移。
     待并行会话稳定后，再把这个 helper 合并回 `render.js`（届时是纯重构，风险低）。

5. **`scriptId` 可为 `null`**：实测 `finishEpisode` **不对 `scriptId` 查库**，仅用于文件名 slug（`slugify(\`${scriptId}_${code}\`)`）与 TTS 的 `outKey`。
   故传 `null` 不会报错，但产物文件名会变成 `null_canvas_*`。建议传真实 `scriptId`，或传画布派生的可读标识。
6. `timeline` 节点执行必须**并发 1**（与 P3 的 `type:'graph'`、现有 `type:'assemble'` 的 `limit:1` 一致）。
7. 写 `episode_films` 用 `try/catch` 包裹，**失败只记日志**，不影响成片结果与节点状态。
8. `spreadEpisodeToCanvas` **绝不发起生成调用**——它只是布局，生成一律走 P4 闸门。
9. `shot` / `timeline` 节点类型必须**按需创建**，**禁止**新画布自动铺满（否则打断 `canvas-audit.py` 中 `items == n_actors` 三处断言）。

### 与清单的差异（均为实测驱动的修正）

1. **端口数 10 → 24**：一集 17~24 镜是常态（演示剧本 S01E001 就是 17 镜），10 个槽位不够。`TIMELINE_PORTS` 扩到 `clip1..clip24`，后端/前端端口表同源更新。
2. **超长分集自动分块**：镜头数 > 24 时建多个成片节点（标题带 `（1/2）`），块内仍从 `clip1` 起编号；有断言覆盖 26 镜 → 2 块（24 + 2）。
3. **`spreadEpisodeToCanvas` 同时铺关键帧节点**：视频节点必须有首帧，否则本地 `placeholder` 与云端后端都会诚实报错（实测报「缺少可用关键帧」）。现在每个镜头建「关键帧（出图）→ `image`/`first` → 视频片段」两节点一条类型化边，画布图因此可**直接执行**：17 关键帧 + 17 视频 + 1 成片。
4. **分镜容器 → 视频片段改用语义连线**（不带端口）：清单里 `shot.out=['clip']` 但没有合法的视频输入端口可接，写死会留下非法端口脏数据。
5. **`ctx.setProgress` 只报百分比**：成片的 4 个子步骤曾把**任务级** `done/total` 覆盖成 4，进度条随之错乱（真实跑图时观察到「27/35 却显示 25%」）。现在子步骤只上报百分比，并可用 `params.onStep` 观测；已加断言「单节点图任务总数 = 1」。
