## 二、痛点清单

### P0（阻塞 / 高风险）

#### P0-1 无版本控制，用 127 个 `.bak` 代替 Git 历史

- **现象**：工作区没有 `.git`；同一文件存在多个时间点副本（`README.md` 有 10 个备份，`web/views/settings.js` 有 7 个，`config/` 有 7 个）。
- **证据**：附录 A-1 输出 `git repo: false`；备份分布 `docs=42 | tests=41 | .（根）=12 | web/views=11 | config=7 | scripts=7 | strategist/runs=4 | web/lib=2 | src=1`。
- **影响**：任何改动不可 diff / 不可回滚 / 不可并行协作；一次误操作只能靠找 `.bak`；`tests/` 里混着 41 个旧版测试，容易被误跑并得出错误结论。
- **整改方案**：
  1. `git init` 并先改 `.gitignore`（见 P0-4 的清单），再 `git add` 代码与文档。
  2. 把 127 个备份整体移到 `_archive/backup-YYYYMMDD/`（不入库），保持原目录只剩当前版本。
  3. 首次提交范围：`src/ web/ tests/ scripts/ config/config.example.json docs/ README.md server.js package.json`；**不含** `data/`、`bin/`、`node_modules/`、`_archive/`。
- **验收标准**：`git log --oneline` 至少 1 条提交；`git status --short` 干净；`find . -name "*.bak*" -not -path "./_archive/*"` 输出为空；`git ls-files | wc -l` 不含 `data/`、`bin/`、`node_modules/`。

#### P0-2 核心业务源码混淆，改动只能"包一层明文"

- **现象**：`src/` 84 个 JS 里 **64 个是单行混淆文件**，承载了编排、排产、自愈、MCP、视觉质检、画布 DAG 等核心逻辑；本机所有新功能都只能做成明文包装层。
- **证据**：附录 A-3 输出 `obfuscated: 64 | plaintext: 20`；Top 列表见上文仪表盘。
- **影响**：已经产生实际代价——为避免改混淆文件，同一逻辑被**重实现了一遍**：`consistency.js` 的 pHash 打分（重写为 `canvas-consistency.js`）、占位出图（重写为 `pngd.js` 渲染占位 PNG）、提示词规则（重写为 `prompt-quality.js`）。修一个 bug 要先判断"这条逻辑在混淆层还是影子层"，且两边容易漂移。
- **整改方案（三选一，**推荐 A**）**：
  - **A（推荐）**：明文层为唯一开发面，混淆产物只作交付件；写死规则——**禁止在混淆文件内新增逻辑**，所有新需求走明文模块 + 模块地图。
  - B：按"改动频率"逐个重建可读源码，优先 `src/studio.js`、`src/schedules.js`、`src/vision-qc.js`。
  - C：冻结混淆核心，全部新功能继续走包装层，并补一份 `docs/模块地图.md` 标明每个混淆文件负责什么、边界在哪。
  无论选哪个，先补**模块地图**（混淆文件 → 责任 → 对外接口 → 已知包装层），避免影子层继续无序膨胀。
- **验收标准**：`docs/模块地图.md` 覆盖全部 64 个混淆文件；新增 PR/提交中不再出现对混淆文件正文的编辑（可用 `git diff --numstat` 对混淆文件行数变化做检查）；重实现的重复逻辑在文档中登记并标注"以哪一份为准"。

#### P0-3 服务端零鉴权 + 配置备份未进忽略清单

- **现象**：`src/http.js` 没有任何 token/auth 校验；服务默认绑 `127.0.0.1`（尚安全），但 `HOST` 一旦改成 `0.0.0.0` 就等于把「付费出图 / 出片」接口全公网开放。`config/` 下 11 个 `config.json.*` 备份没有被 `.gitignore` 覆盖。
- **证据**：`src/http.js` 全文无 `token|authorization|auth`；附录 A-5 输出 `secret-ish fields: 69 | non-empty: 0`（**当前没有任何非空密钥**）；附录 A-6 输出 `config.json.bak → NO`。
- **影响**：当前是**潜在**风险而非已泄露；一旦有人往设置页填了 API Key，这些未忽略的备份会被一并提交/打包外发。局域网/端口转发场景下，无鉴权接口可被任意调用（含花钱动作）。
- **整改方案**：
  1. `.gitignore` 增补 `config/*.bak*`、`config/config.json.*`（保留 `config.example.json`）。
  2. 删除或移出 `config/config.json.ark-broken`、`.backup-bailian-verified`、`.bak*`、`.before-offline-png` 等 11 个历史配置。
  3. 新增 `scripts/check-secrets.mjs`：扫描 `config/**`、`*.json`，发现非空 `*key|*secret|*token|*password` 即非零退出，作为提交前检查。
  4. 若将来需要对外暴露：给服务加一层 token 中间件（`Authorization: Bearer`），并把 `HOST=0.0.0.0` 与"无 token"组合直接拒绝启动。
- **验收标准**：`node scripts/check-secrets.mjs` 退出码 0；`git check-ignore -v config/config.json.bak` 命中；`ls config/*.bak*` 无输出；文档中记录"对外必须带 token"的启动约束。

#### P0-4 数据目录未治理：870 MB 且大部分未被忽略、无保留策略

- **现象**：`data/` 占 680 MB+，其中交付包 417 MB；`.gitignore` 只忽略了 `data/*.db`、`data/images/**`、`data/uploads/**`。
- **证据**：附录 A-2 的 data 明细；附录 A-6 输出：`deliveries → NO`、`videos → NO`、`finish → NO`、`thumbs → NO`、`publish → NO`、`subtitles → NO`、`render → NO`、`cache → NO`、`*.zip → NO`。
- **影响**：一旦执行 `git add .`，会把 GB 级产物与 133 个交付包提交进仓库；同时磁盘只增不减，备份/打包体积会持续膨胀。
- **整改方案**：
  1. `.gitignore` 增补：`data/deliveries/`、`data/videos/`、`data/finish/`、`data/thumbs/`、`data/publish/`、`data/subtitles/`、`data/render/`、`data/cache/`、`*.zip`、`.tmp-*`。
  2. 新增 `scripts/prune-data.mjs --dry-run`：默认只读预览，按「每类保留最近 N 个 + 总容量上限」计算可清理项；真正删除需显式 `--apply`。
  3. 建议默认阈值：`deliveries` 保留最近 20 个且总量 ≤ 5 GB；`images` 保留被引用图（`actors.ref_image` / `actor_images.file_path` / `shots` 引用）+ 最近 30 天；`finish` 保留最近 10 集成片。
- **验收标准**：`git status --short` 在生成新交付包后仍为空；`node scripts/prune-data.mjs --dry-run` 能列出可回收字节数；执行一次 `--apply` 后 `data/deliveries` 数量与体积不超过阈值且系统功能不受影响（用一次全量模拟复核）。

### P1（影响交付效率与质量）

#### P1-1 前端巨型单文件，无组件化 / 无类型 / 无 lint

- **现象**：`actors.js` 5,351 行、`render.js` 3,227 行、`script.js` 1,394、`novel.js` 1,277、`studio.js` 1,267、`settings.js` 1,146。
- **证据**：附录 A-4。
- **影响**：单文件内 CSS/状态/渲染/事件全混；改一处要通读全文；无法做单元测试；新人上手成本高；多人在同一文件上必然冲突。
- **整改方案**：先立规则后重构——按"视图壳 + 子面板模块 + 纯逻辑（`web/lib/*`）"三层拆分，优先拆已经抽出纯逻辑的两个（`canvas-select.js` 已是先例）；同时引入 `eslint`（仅规则校验，不改格式）与 `editorconfig`。
- **验收标准**：任一新拆模块 ≤ 800 行；`canvas-select.test.mjs` 模式可复用于新拆纯逻辑模块；`npx eslint web/` 无 error。

#### P1-2 测试不可一键跑，环境依赖散落（已在附录 D 整改）

- **现象**：没有 `npm test`；多个套件必须手工注入环境变量；`tests/` 里还有 5 个 Python 脚本（本机无 Python/Playwright，实际不可跑）。
- **证据**：
  - 裸跑 `node tests/test-script.js` → `Error: unable to open database file`（默认写 `/tmp/...`，Windows 下解析为不存在的 `C:\tmp\`）。
  - 加上 `FACTORY_DB` + `FACTORY_DATA_DIR` + `SKIP_REAL_LLM=1` 后 → **75 通过 / 0 失败**。
  - `tests/test-graph.js` 需要 `bin/ffmpeg` 进 PATH，否则 12 项失败（我在评估中复现过）。
  - Python 套件：`canvas-audit.py`、`make-audit-refs.py`、`ui-scale.py`、`ui-simulate.py`、`ui-smoke.py`。
- **影响**：新机器/新成员"跑测试"是手工活，回归靠人记命令；CI 无从谈起。
- **整改方案**：
  1. 新增 `scripts/run-tests.mjs`：自动设置 `FACTORY_DB`/`FACTORY_DATA_DIR`（指向临时目录）、把 `bin/ffmpeg` 前置进 `PATH`、默认 `SKIP_REAL_LLM=1`，逐个 Node 套件串行跑并汇总。
  2. `package.json` 增 `"test": "node scripts/run-tests.mjs"`、`"test:sim": "node scripts/simulate-all.js"`。
  3. 修掉 `tests/test-script.js` 的 `/tmp` 硬编码，改成 `os.tmpdir()`。
  4. Python 套件显式标记为"可选"，在文档与脚本里区分 `node` 与 `python` 两组，缺失 Python 时跳过并给出提示。
- **验收标准**：`npm test` 在干净检出上一条命令跑完并输出汇总（当前应为 800+ 断言、0 失败）；`npm run test:sim` 输出 `83 通过 / 0 失败`；无 Python 环境时脚本提示跳过而不是报错。

#### P1-3 测试写死实现细节 + 备份污染 `tests/`（已在附录 D 部分整改）

- **现象**：`tests/` 下有 41 个 `.bak`；已有断言把实现细节当成契约。
- **证据**：本轮实测中 `tests/test-render.js` 的 `16-③` 断言 `real.cache.freedMB > 0`，在"占位出图改为 PNG（不再需要 ffmpeg 栅格化 → `cache/refs` 为空）"后失败；改为按字节如实换算的不变量后 **151/0**。备份分布见附录 A-1（`tests=41`）。
- **影响**：实现优化会误伤测试，制造"测试假红灯"，削弱对红灯的信任；`.bak` 混在套件目录里，误跑旧版会得出错误结论。
- **整改方案**：断言只写"契约/不变量"（字段存在、口径自洽、可复现），不写具体字节量级；把 41 个测试备份移入 `_archive/`（同 P0-1）；在 `scripts/run-tests.mjs` 里对文件名做黑名单（含 `.bak` 的直接跳过）。
- **验收标准**：`tests/` 下无 `.bak`；`npm test` 输出中不出现被跳过的备份文件；修改实现细节（如缓存策略）后不需要改断言即能通过。

#### P1-4 文档臃肿且已出现漂移

- **现象**：`docs/` 20 个 md + 42 个备份文件，根目录 `README.md` 57 KB + 10 个备份，多本手册内容互相重叠（`使用手册.md` 117 KB、`模型对接参考.md` 183 KB、`排产与自愈使用手册.md` 64 KB）。
- **证据**：附录 A-1 的 docs=42 备份；本轮我在维护计划书时就发现测试数字过期（`test-script.js` 记成 69，实际 75）并现场修正。
- **影响**：同一事实存在多份且不同步；接手者不知道以哪份为准。
- **整改方案**：确立单一事实源——产品说明以 `docs/使用手册.md` 为准、模块说明以 `docs/模块N-使用说明.md` 为准；其余改造清单类文档标注"历史归档"并移入 `docs/archive/`；README 只保留安装/启动/测试/目录结构四段。
- **验收标准**：`docs/archive/` 收走历史文档；`README.md` ≤ 8 KB；文末附录的命令能原样跑通所有被引用的数字。

#### P1-5 反馈环偏慢

- **现象**：全量离线模拟 109.5 s，`test-render` 34.0 s，`test-graph` 4.0 s，`test-novel` 6.5 s，累计单轮 ~2.5 min（不含 Python）。
- **证据**：见仪表盘「基线测试」耗时列。
- **影响**：改一行要等 2 分钟以上才有结论，容易跳过回归。
- **整改方案**：`scripts/run-tests.mjs` 支持分层——`--fast`（纯逻辑：canvas-select / canvas-perf / prompt-quality / describe / canvas-consistency，秒级）、`--full`（含 simulate-all / render / graph）。默认 `npm test` 跑 fast，提交前跑 full。
- **验收标准**：`npm test -- --fast` 在 20 s 内出结果且 0 失败；`npm test -- --full` 输出与当前基线一致。

### P2（体验与规模）

#### P2-1 两条成片线代码重复

- **现象**：画布（`timeline.js` + 画布 timeline 节点）与制作台（`modules/render.js` + `finish.js`）各有一套"排片 → 合成成片"路径。
- **证据**：`src/timeline.js` 导出 `spreadEpisodeToCanvas / timelineOrderPreview / reorderTimelineClips / executeTimeline`；`src/finish.js` 导出 `finishEpisode / applyAudio / applySubtitles`。UI 侧现在只靠入口按钮区分职责（制作台顶栏「去剧本工厂 / 去画布精修」、画布「去制作台」）。
- **影响**：同一能力要修两处；行为不一致时用户难以判断"以哪条线为准"。
- **整改方案**：明确"制作台 = 批量自动出片；画布 = 手工精修与二次导出"，并把画布时间线定位为**导入剧本分镜后精修**；在两处代码注释与模块地图中写清边界，长期把成片合成收敛到单一实现。
- **验收标准**：模块地图中两条线的职责与调用关系成文；同一成片需求只需改一处（可用一次 changelog 验证）。

#### P2-2 大项目性能

- **现象**：导出（FDX / HTML / OTIO / EDL / FCPXML）一次性在内存拼装；镜头表只有分页（25/50/100/200）没有虚拟滚动。
- **证据**：`src/routes/scripting.js` 中 `fdxOf/htmlOf/otioOf/edlOf/fcpxmlOf` 均返回整串字符串后一次性写响应；`web/views/script.js` 的分页实现为 `pagedShots()` 切片渲染。
- **影响**：数百镜一集时内存与首屏都会变差；导出大项目会明显卡顿。
- **整改方案**：导出改为流式写（分块 `res.write`），镜头表在分页之上加窗口化渲染（只渲染可视行）。
- **验收标准**：1000 镜项目导出峰值内存不随镜头数线性增长；镜头表滚动 60 fps 无长任务告警。

#### P2-3 无 CI 门禁

- **现象**：无 `.github/workflows`、无 lint、无格式化校验，回归完全靠人工。
- **证据**：附录 A-6 输出 `.github: false`。
- **影响**：回归靠自觉；"我这边是好的"无法自动化证伪。
- **整改方案**：先有 `npm test`（P1-2），再加最小 CI：跑 `npm test -- --fast` + `node scripts/check-secrets.mjs` + `git diff --check`。
- **验收标准**：CI 在 PR 上红/绿可复现；密钥检查能在含假 key 的临时分支上正确失败。
