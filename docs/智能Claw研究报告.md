# 智能 Claw（OpenClaw / Clawdbot）研究报告 —— 与 ai-video-factory 的技术对照与落地建议

> 调研对象：**OpenClaw**（原名 Clawdbot，短暂改名 Moltbot，最终定名 OpenClaw）——开源自托管的个人 AI 助手 / Agent 框架。
> 调研时间：2026-09-27。用途：为本项目的「自动化制片 Agent」选型与加固取经，**只借思路，不引入依赖**（本项目坚持零外部依赖的 Node ≥22 ESM 栈）。
> 主要来源：[OpenClaw 完全指南](http://www.chuangze.cn/attached/file/20260313/20260313111515291529.pdf)、[OpenClaw Agent harness 核心所有权](https://docs2.openclaw.ai/plugins/sdk-agent-harness/core-ownership)、[Sandboxing 能力矩阵](https://docs2.openclaw.ai/gateway/sandboxing/supported-capability-matrix)、[Clawdbot 给 AI Agent 的教训](https://skywork.ai/blog/ai-agent/clawdbot-lessons-ai-agents/)、[OpenClaw 是什么](https://skywork.ai/blog/ai-agent/what-is-clawdbot-openclaw/)、[Clawdbot 深度解析与部署](https://developer.aliyun.com/article/1716137)、[从 Agent 到 Skills 的范式转变](https://news.qq.com/rain/a/20260330A02QOR00)。

## 一、它到底是什么（一句话）

一个**自托管、常驻、以「技能（Skills）+ 工具（Tools）+ 网关（Gateway）」为骨架的个人 Agent 运行时**：Agent 不是写死的业务系统，而是「一个会调用技能与工具的循环」，把权限、沙箱、审批、长时任务、记忆都做成了运行时的**基础设施**，而不是每个业务各自实现一遍。

## 二、值得抄的七个设计（按对本品价值排序）

### 1. Skills 优先，而不是 Agent 优先
社区那句口号「**Stop Building Agents, Start Building Skills**」是核心洞见：把一个领域能力写成**可复用的技能包**（声明式的输入输出 + 步骤 + 依赖工具 + 失败处理），Agent 只是技能的编排者。

**对本品的映射**：我们已经有 31 个 MCP 工具（`canvas_*` / `job_*` / `studio_*`），但「怎么把它们串成一件正事」目前写在 `src/studio.js` 里（十个阶段的硬编码流程）。可以再抽一层 **`skills/`（纯声明）**：`skills/produce-vertical-drama.skill.json` 描述「一句话需求 → 十阶段 → 交付包」，把「阶段顺序、依赖、是否付费、失败策略」变成**数据**而不是代码。收益：换一种剧（横屏电影、儿童动画、有声书）只加技能文件，不动引擎；也便于 Agent 自己发现与组合技能。

### 2. 能力矩阵 + 权限分级（capability matrix）
OpenClaw 把「每个能力在每种沙箱/宿主下是否可用」列成**矩阵**，先把边界说清楚，再谈自动化。

**对本品**：我们已有 `TOOL_LEVELS = {read, plan, canvas, exec}` 与「付费工具」标记，并且把 `canvas_run / studio_resume` 设成**需要人类确认码**。建议补齐一张**显式的能力矩阵文档 + 机器可读接口**（`GET /api/capabilities`）：能力 × 前置条件（LLM Key / 出图后端 / 视频后端 / TTS / ffmpeg / 磁盘余量）× 是否计费 × 是否需要人类确认。界面据此显示「现在能做什么、缺什么」，Agent 也据此避免调用注定失败的能力（比事后报错友好得多）。

### 3. 「运行时拥有核心」而不是插件各自为政（core ownership）
OpenClaw 的 harness 明确划出**谁拥有会话、谁拥有工具调用循环、谁拥有超时与中断**，插件只提供能力，不接管生命周期。

**对本品**：我们有 `src/jobs.js`（持久化队列 + 进度 + 取消 + SSE）与 `src/graph.js`（DAG 执行 + 输入指纹增量）。**应坚持**：所有阶段执行都必须经队列（可取消、可观测、可自愈），技能/插件只声明做什么。本轮已经做到了（制片流水线的每个阶段都进 `type:'studio'` 队列；画布节点执行进 `type:'graph'`）。

### 4. 花钱的动作一律「可预演 + 需人类放行」
Clawdbot 的教训里最常被引用的一条：**Agent 的自由度必须与副作用成正比地受限**。

**对本品**：这正是我们已经落地的**四道闸门**（人工 approve → 人类确认码 → 执行前二次比对计划 → 预算闸门），并且实测反证过「未批准时执行记录 0 / 新任务 0」。本报告建议再加两条：
- **dry-run 费用预演**：付费阶段在批准界面上直接给「按当前后端单价 × 调用次数」的金额区间（已有 `estimate`，缺「单价未配置」时的显式提示 ✅ 已补）；
- **额度/配额熔断**：`guard.js` 已有月度上限，建议再加**单次制片预算上限**（一个制片项目的总花费上限，超过就拒绝整条流水线而不是拒绝单步）。

### 5. 长时任务与「人不在场也能继续」
个人助手的实际用法是「交代一句就走开」。这要求：任务持久化、进程重启可续、进度可查、失败可重试、**关键决策点能等人回来**。

**对本品**：`recoverStaleJobs`（重启自愈）+ 阶段幂等 + `reconcileStages`（放行后的阶段任务结束即回写终态）已经覆盖大半；**还缺一条**：付费阶段等待批准时的**超时策略**（现在是无限等待）。建议：计划 30 分钟过期（P4 已实现 `PLAN_TTL_MS`）→ 制片阶段在计划过期后**自动回到 `awaiting_approval` 之外的状态**并给出「计划已过期，请重新生成」的明确提示，避免用户回来看到一张假等待的界面。

### 6. 记忆与「结构化留痕」
OpenClaw 强调把会话、工具调用、产物都落成**可检索的记录**，而不是只保留最终答案。

**对本品**：我们已经有三层记录（`canvas_node_runs` 节点执行 / `production_stages` 制片阶段 / `canvas_plan_audits` 审批审计）。建议补**一次制片的「一页纸」报告**（`data/productions/<id>/report.md`）：解析出的需求、每个阶段耗时与产物、实际调用次数与金额、质检结论、交付包清单——既是交付物，也是下次调优的输入。

### 7. 场景隔离（TTS/音乐/音效分场景、模板与工作流分离）
OpenClaw 的能力矩阵把「同一类能力的不同场景」分开治理（例如不同的运行环境、不同的权限档）。

**对本品**：视频后端已经分了 `placeholder / comfyui-h3 / generic-http`，音频也分了 `tts / file / bgm`。建议把「**场景**」显式化到节点上（`data.scene = 对白/旁白/音效/BGM`），让配音链路按场景选后端与音色（现在只按演员音色），这也顺带解决「画外音被当台词」这类语义问题。

## 三、不建议抄的部分（与本项目定位冲突）

| OpenClaw 的做法 | 为什么不抄 |
|---|---|
| 插件生态 + 运行时热插拔 | 本项目定位是**单机自用、零依赖**，引入插件生命周期会带来版本兼容与安全面 |
| 多通道（IM/语音/多端）接入 | 我们的入口是本地 Web GUI + MCP，不需要付出多通道维护成本 |
| 通用自主循环（无约束地自己决定下一步） | 制片是**强副作用**（花钱、耗时、产出交付物），必须走「阶段化 + 闸门」，不能交给自由循环 |
| 把密钥/凭据托管到运行时 | 我们坚持 Key 只存本地 `config.json` / `~/.dsh/.credentials.yaml`，不落库、不出网 |

## 四、落地清单（按性价比排序，均已与本仓库现状对齐）

1. **P0 · 技能化**：把 `src/studio.js` 的十阶段流程抽成 `skills/*.skill.json`（阶段、依赖、付费标记、失败策略、默认参数），引擎读技能文件驱动 —— 换剧型只加文件。
2. **P0 · 能力矩阵**：新增 `GET /api/capabilities`（能力 × 前置条件 × 计费 × 是否需确认），界面用它渲染「现在能做什么」与缺口提示。
3. **P1 · 单次制片预算**：`guard.js` 增加 `productionCap`，超限时拒绝整条流水线并说明已花费/上限。
4. **P1 · 等待批准的过期策略**：制片阶段在计划过期后明确报「计划已过期，请重新生成」，不留假等待。
5. **P1 · 一页纸制片报告**：每完成一次制片产出 `data/productions/<id>/report.md`（需求 → 阶段 → 产物 → 花费 → 质检 → 交付包）。
6. **P2 · 场景化音频**：音频节点 `data.scene`（对白/旁白/音效/BGM），配音按场景选后端与音色。
7. **P2 · 技能自发现**：MCP 增加 `skills_list` / `skill_run`，让外部 Agent 能列出并执行本项目的技能（与现有工具并列）。

## 五、与现有实现的对照（一眼看差距）

| 能力 | OpenClaw | ai-video-factory 现状 |
|---|---|---|
| 工具面 | 插件 + 工具 + 技能 | ✅ 31 个 MCP 工具（read/plan/canvas/exec 四级） |
| 人类闸门 | 权限与沙箱档位 | ✅ **四道闸门**（批准 + 确认码 + 计划再比对 + 预算），实测反证未批准零调用 |
| 长时任务 | 常驻运行时 | ✅ 持久化队列 + 重启自愈 + 阶段幂等 + 状态对账 |
| 增量执行 | 上下文/记忆 | ✅ 输入指纹增量跳过，绝不重复计费 |
| 技能声明 | Skills 包 | ⚠️ 流程仍硬编码在 `src/studio.js`（建议抽成技能文件） |
| 能力矩阵 | 有成文矩阵 | ⚠️ 只有分散的后端就绪状态（建议出 `GET /api/capabilities`） |
| 结构化留痕 | 会话/工具记录 | ✅ 三层记录 + 交付包；⚠️ 缺「一页纸制片报告」 |
| 场景隔离 | 能力场景分治 | ⚠️ 音频节点已有 tts/file/bgm，未到「对白/旁白/音效」级 |

## 六、结论

OpenClaw 真正的贡献不是「让 Agent 更自由」，而是**把 Agent 的副作用治理做成基础设施**：声明式技能、成文能力矩阵、运行时拥有核心循环、沙箱与权限分级。这与本项目做「自动化制片 Agent」时踩出来的结论完全一致——**能自动的都自动化，花钱的必须人类点头**。

因此本报告的落地建议集中在三件事：**把流程变成技能文件（可组合）、把能力边界变成可查询的矩阵（可预判）、把每次制片变成一页纸报告（可复盘）**。其余（插件生态、多通道、无约束自主循环）与本项目的单机自用定位冲突，明确不引入。
